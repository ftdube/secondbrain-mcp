# Risk Register — SecondBrain MCP Server

Companion to [`BRD.md`](BRD.md), which defines the `FR-*`/`NFR-*` requirement IDs referenced below. Extracted from BRD.md §14 in document v1.9 to keep the BRD a requirements document, not a running log — a risk is an operational/historical fact, not a requirement.

Entries carrying a `(Resolved in document vX.Y)` tag were resolved while this table still lived inside `BRD.md`, before the v1.9 extraction — that tag is a historical pointer to the BRD version at the time, not an ongoing versioning scheme for this file. New entries added here going forward SHOULD use a plain date instead.

| ID | Risk | Likelihood | Impact | Mitigation / Status |
|---|---|---|---|---|
| RISK-1 | *(Resolved in document v1.2)* `search`'s own docstring/README claimed "top 5" results while the implemented `LIMIT` was 10. | — | — | **Resolved** — docstring (`server.py`) and `README.md` now say 10, matching `FR-SRCH-2` and the actual `LIMIT`. No runtime behavior changed. Tracked as [issue #36](https://github.com/ftdube/secondbrain-mcp/issues/36). |
| RISK-2 | *(Resolved in document v1.4)* `read_note` had no size cap; one very large note could consume a disproportionate share of a session's token budget. | — | — | **Resolved** — `read_note` now caps responses at `READ_MAX_CHARS` (20,000 chars) with an explicit truncation marker (FR-READ-4, NFR-READ-2). Tracked as [issue #37](https://github.com/ftdube/secondbrain-mcp/issues/37). |
| RISK-3 | `/reindex` is intentionally unauthenticated; if `MCP_BASE_URL` were ever exposed without the existing OAuth-fronted ingress, any anonymous caller could trigger repeated reindex load. | Low | Low (rebuild cost only, no data exposure) | Keep `/reindex` behind the existing ingress; do not expose it as a separate public route |
| RISK-4 | JWKS keys are cached in-process; a Dex signing-key rotation without a coordinated pod restart causes a window of `401`s for every client. | Low (infrequent rotation) | Medium (full-service outage until restart) | Documented operational runbook step in `agents.md` |
| RISK-5 | Multi-file proposal atomicity (FR-PROP-8) depends entirely on `apply_proposals.py`'s check-before-apply discipline, not on `git` itself. A future edit calling `apply_one()` without a preceding `check()` would silently reintroduce partial-apply risk. | Low | High (could corrupt vault notes) | NFR-PROP-8 + regression test `test_multi_file_patch_atomic_when_one_file_drifted`; documented as a hard invariant in `agents.md` |
| RISK-6 | No per-note authorization exists; any authenticated principal can read or propose edits to the entire vault. | N/A under current single-user model | High if the deployment model ever becomes multi-user | Explicitly out of scope (BRD.md §4.2); revisit if multi-user support is ever pursued |
| RISK-7 | *(Resolved in document v1.4)* Concurrent `apply-proposals` runs were not guarded; two overlapping invocations (e.g. a cron job and a manual run) could interleave `check()`/`apply()` steps across processes. | — | — | **Resolved** — `scripts/apply_proposals.py` now takes an exclusive, non-blocking `flock` on `<repo>/.apply_proposals.lock` for the whole run; a second concurrent invocation exits immediately (code 3) without touching any patch or note. Tracked as [issue #38](https://github.com/ftdube/secondbrain-mcp/issues/38). |
| RISK-8 | *(Resolved in document v1.4)* The authentication middleware (`BearerAuthMiddleware`, JWT validation, public-path allowlist) had no automated test coverage. | — | — | **Resolved** — `tests/test_auth.py` now covers FR-AUTH-1..6 and NFR-AUTH-5/6 against the real `BearerAuthMiddleware` class, using a generated RSA keypair and a mocked `PyJWKClient`. Tracked as [issue #39](https://github.com/ftdube/secondbrain-mcp/issues/39). |
| RISK-9 | *(Resolved in document v1.8, same-day as introduction)* `VAULT_BLACKLIST`'s initial implementation (v1.7) parsed entries with a raw `Path(p).parts`; a leading-slash entry (e.g. `/Health/Psychology` instead of `Health/Psychology`) produced `("/", "Health", "Psychology")`, which never matches a real relative path — a plausible operator typo would silently blacklist nothing. Elevated to a risk-register entry (not just a bug note) because the failure mode is silent and the feature's whole purpose is hiding sensitive content — a false sense of "this is hidden" is worse than an error. | Low (caught same-day, pre-merge) | Would have been High had it shipped (silent exposure of content the operator believed was excluded) | **Resolved** — `_parse_blacklist` strips leading slashes before matching; regression-tested (`test_parse_blacklist_strips_leading_slashes`). Tracked as [issue #55](https://github.com/ftdube/secondbrain-mcp/issues/55). |
| RISK-10 | *(Resolved in document v1.11, same-day as introduction)* `propose_edit`'s v1.10 file-creation feature (FR-PROP-6/9) reused NFR-PROP-9's dummy git-blob-hash trick, which safely rejects drift on *edits* to existing files. It does not, by itself, protect *creates*: a create diff declares its base directly as `/dev/null` rather than resolving it via the index line's blob hash, so `git apply --3way` could always reconstruct an empty base and perform a genuine 3-way merge on a drifted create-target — silently writing `<<<<<<<` conflict markers into the file on disk while `apply_proposals.py check()` still reported it clean. Found empirically in a post-implementation gap audit (a scratch-repo test that independently created the target between drafting and applying), before this feature had been used against the real vault. | Low (caught same-day, pre-merge, in a gap audit specifically run to catch this class of issue) | Would have been High had it shipped (silent corruption of a real note the operator believed was a clean create) | **Resolved** — `apply_proposals.py` now rejects a create whose target already exists on disk as drift, before the patch is ever handed to `git`; regression-tested (`test_check_stale_when_create_target_already_exists`, `test_drifted_create_apply_never_writes_conflict_markers`). |
| RISK-11 | *(Added document v1.12)* `git-sync` (read-only pull sidecar) and `push-sync` (read-write) currently share the identical SSH deploy key in `compose.yaml` (`x-ssh-key` anchor), documented as intentional in `README.md`. If that key carries push rights, as it must for `push-sync` to function, a compromise of the `git-sync` container — the sidecar most directly exposed to the vault's git remote — would hand an attacker write access to the vault repository, even though `git-sync`'s own logic never pushes. Found via a comparative gap audit against `vault-publisher`'s `NFR-SEC-2`, which requires the equivalent sidecar there to hold no push credentials at all. | Medium (depends on how the deploy key is provisioned upstream; plausible default is a single read-write key for simplicity) | Medium (full vault git write access, not just read exposure, on compromise of the more network-exposed sidecar) | **Resolved** — `BRD.md` NFR-SEC-7 implemented in PR #62; `git-sync` now uses a separate `GITSYNC_SSH_KEY_PATH` instructed to be read-only. Tracked as [issue #58](https://github.com/ftdube/secondbrain-mcp/issues/58) |
| RISK-12 | *(Added document v1.12)* `/health` (`server.py`) always returns `{"status": "ok"}`, with no signal for whether the first FTS5 index build has completed. A fresh pod (initial deploy, or restart against an empty `DB_PATH`) could pass a K8s readinessProbe and start serving `search`/`read_note` against an empty index, returning `"No results."` for everything with no way to distinguish that from a genuine miss. Found via a comparative gap audit against `vault-publisher`'s explicit readiness/liveness split (its own RISK-2). | Low (narrow window: only fresh starts/restarts; single-operator deployment would likely notice quickly) | Low (self-corrects once the first reindex completes; no data exposure or corruption) | Open — `BRD.md` FR-OBS-1 (Not implemented). Tracked as [issue #59](https://github.com/ftdube/secondbrain-mcp/issues/59) |
| RISK-13 | *(Added document v1.12)* No metric exposes time-since-last-successful-reindex. If `git-sync` silently stops pulling (expired deploy key, network partition, upstream repo rename), the server keeps serving increasingly stale content well beyond `NFR-COM-5`'s ~5.5 minute expected bound, with no Prometheus-visible signal — unlike the proactive miss-rate alert `NFR-SRCH-3` already provides for search quality. Found via a comparative gap audit against `vault-publisher`'s BRD. | Low (git-sync failures are themselves uncommon) | Medium (an extended, silent outage could go unnoticed indefinitely — the exact failure mode a staleness metric exists to catch) | Open — `BRD.md` NFR-OBS-1 (Not implemented). Tracked as [issue #60](https://github.com/ftdube/secondbrain-mcp/issues/60) |
| RISK-14 | *(Added document v1.12)* No formal RAM bound or K8s `resources.requests`/`resources.limits` exist for this service; `BRD.md` `G6`'s "~80 MB" is an observed, not enforced, figure. An unbounded pod could in principle starve co-located workloads on the same constrained cluster — the same real problem `vault-publisher`'s BRD.md §2 describes as a prior motivation for its own explicit RAM bounds (NFR-POLL-1/NFR-BUILD-1). | Low today (footprint is small in practice per G6) | Low–Medium if the vault or index grows substantially, or if co-located workloads on the same node grow | Open — `BRD.md` NFR-OBS-2 (Not implemented). Tracked as [issue #61](https://github.com/ftdube/secondbrain-mcp/issues/61) |
